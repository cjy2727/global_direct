# API 아키텍처

## 현재 구현

외부 클라이언트 -> Nginx:80 -> PHP-FPM -> Playwright:3000 -> 상품 페이지.
public/index.php는 CORS, JSON 검증, 라우팅 및 오류 응답을 처리합니다.
src/ProductService.php는 URL 검증 후 worker 결과 전체를 반환합니다.
src/bootstrap.php는 클래스 로딩 및 환경 변수 조회만 담당합니다.

상품 DB/Redis에 저장하지 않으며 일반 사용자 세션 쿠키를 발급하지 않습니다. 운영자 로그인은 별도 포트에서 전용 세션 쿠키를 사용합니다.
작업 대기열·진행 중 요청 통합·결과 캐시는 단일 Node 워커 메모리에서 관리합니다. AI 일일 사용량은 별도 `analysis-state` 볼륨에 파일로 보존합니다.
기존 동기 API와 신규 비동기 작업 API가 같은 작업 관리자를 사용합니다. PHP의 worker 호출 제한은 250초이며, 분석과 대기 제한의 설정 최대값(각 120초)보다 깁니다.
일반 사용자 화면, 회원, 장바구니, 주문 기능은 제공하지 않습니다.
기존 MySQL/Redis 데이터 볼륨은 보존합니다. API 계약은 README.md를 참고하세요.

## 공개 서비스 처리 구조

홈페이지의 공개 상품 분석을 위한 처리 흐름은 다음과 같다.

홈페이지 요청 -> 요청 제한 -> 캐시·진행 중 작업 확인 -> 작업 대기열 -> 동시 실행이 제한된 Playwright 수집 -> 필요 시 AI 보완 -> 결과 검증·옵션 입력 대체 -> 결과 조회.

수집 내부 순서는 운영 Global Shopping API 우선, 기존 Playwright 분석, 부족 시 AI Chromium 탐색이다. `worker/ai-browser.js`는 관찰 가능한 요소 ID와 제한된 조작 도구를 제공한다. `worker/ai.js`는 OpenAI 함수 호출을 실행하고 관찰 결과를 다시 전달하는 반복을 담당한다. 기존 상품 결과는 유지하고 실제 관찰된 옵션·상세만 보완한다. 매 모델 요청은 기존 일일 호출·비용 회계에 포함되며, 함수 호출과 암호화된 reasoning 항목을 요청 메모리에서 이어받고 영구 저장하지 않는다.

- `POST /api/products/jobs`는 분석 작업 ID를 먼저 반환하고, 호출 측은 `GET /api/products/jobs/{id}`로 진행 상태와 결과를 조회한다. 기존 `POST /api/products/analyze`는 동기 응답을 유지한다. 홈페이지는 PHP 연결을 오래 점유하지 않는 비동기 API를 사용한다.
- 같은 상품의 진행 중 요청은 하나로 합치고, 캐시가 활성화되어 있으면 유효한 결과를 재사용한다. 캐시에는 가격·재고 확인 시각을 포함한다.
- 상품 분석과 AI 호출의 동시 실행 수·시간 제한을 각각 적용한다. 대기열은 최대 길이와 최대 대기 시간으로 제한한다.
- 요청 제한·중복 등록·작업 실행은 한 Node 프로세스가 관리한다. AI 한도는 호출 전에 보수적으로 예약하고 파일에 원자적으로 저장한다. 응답 사용량이 있으면 실제 비용으로 조정하며, 실패·사용량 미확인 시 예약액을 유지한다. 파일이 손상되거나 저장할 수 없으면 AI를 건너뛴다.
- AI 미사용이나 AI 한도 초과 시에는 AI 단계만 건너뛰고 기존 수집 결과와 필요한 옵션 입력 항목을 반환한다.
- 설정 항목과 제한 도달 시 동작은 [공개 서비스 운영 제한 설정 정책](PRODUCT.md#공개-서비스-운영-제한-설정-정책)을 따른다.

대기열·캐시·작업 결과·분당 요청 카운터는 재시작 시 초기화된다. AI 사용량은 UTC 날짜별로 보존하고 다음 날 첫 호출에서 전환한다. 여러 워커·서버를 동시에 실행하는 분산 운영은 지원하지 않으며, 그 경우 공유 저장소와 원자적 잠금으로 확장해야 한다. 기존 운영 데이터와 볼륨은 재사용·초기화하지 않는다.

작업 ID는 192비트 난수이며 결과 접근 권한을 가진 비밀값으로 취급한다. URL·작업 ID를 공개 로그나 제3자에게 공유하지 않는다. 결과 조회도 IP별 제한을 적용하고 응답에 `Cache-Control: no-store`를 설정한다. 익명 사용자 식별은 `REMOTE_ADDR` 기준이며 임의의 전달 헤더를 신뢰하지 않는다. 서버 인증으로 설정된 `REMOTE_USER`가 있을 때만 사용자별 제한도 적용한다. 프록시 뒤에서는 Nginx의 신뢰 프록시/실제 IP 설정을 배포 환경에 맞춰 별도 구성해야 한다.

## 운영자 설정

Nginx의 별도 8080 리스너 → `127.0.0.1:3001` 운영자 서버 → 같은 Node 프로세스의 설정 저장소·작업 관리자·AI 회계로 연결한다. 80 상품 API에는 운영자 경로를 추가하지 않는다. 운영자 HTML/JS/CSS는 `worker/admin`에서 제공한다.

`settings.js`는 허용된 운영 설정만 검증하고 파일 교체로 원자적으로 저장한다. 버전 충돌 시 409로 거절한다. 인증정보·암호화 키는 `admin-auth.js`/`admin-setup.js`로 생성하며 비밀번호는 scrypt 해시, 저장된 API 키는 AES-256-GCM 암호문이다. 인증 파일은 최초 등록 시에만 생성하고 자동 덮어쓰기하지 않는다. 시작 시 저장 파일이 손상되어 있으면 기존 파일을 보존하고 시작을 실패시킨다.

운영자 세션은 30분 고정 만료이며 쿠키는 HttpOnly/SameSite=Strict, HTTPS 접속 주소에서는 Secure를 적용한다. 로그인·변경 POST는 지정 Origin과 일치해야 하고, 로그인 이후 변경은 CSRF 토큰도 검사한다. 실패 로그인은 IP별 15분 동안 5회까지 허용한다. 관리 현황에는 상품 URL·작업 접근 ID·원본 AI 응답을 노출하지 않는다. 운영자 계정 초기 등록 외 설정 저장은 재시작을 요구하지 않는다.

환경변수 기본값에 저장된 설정을 덮어 적용하고, 작업 실행 시작 시 불변 사본을 전달한다. 작업별 AI 객체는 설정만 분리하며 활성 호출 수·일일 회계는 하나의 객체로 공유한다. 새 설정 버전에서는 이전 캐시와 작업을 재사용하지 않는다. 동시 실행 수 변경은 다음 작업 배정에 반영하며 진행 중인 작업을 종료하지 않는다. 설정 파일 외부 직접 편집은 자동 감지하지 않으며 관리 API를 통해 저장해야 한다.
